## Method

Three hand-written benchmarks against the crate's public API (`Regex::new` construction, `find_iter` throughput, `is_match` early-exit), run because the crate's own bench suite was moved out of the repo into a separate cross-engine project (`rebar`), and the one remaining in-repo bench file requires nightly Rust, which wasn't available in this environment.

For each commit: checkout → `cargo build --release` → 20 independent process invocations × 2,000 timed iterations (200 discarded as warmup) per benchmark → raw per-iteration nanosecond timings stored with full environment metadata (CPU model string, `rustc`/Cargo version, build duration, timestamps).

Change-point detection uses a two-sided Mann-Whitney U test on each commit's 20 per-run medians against its predecessor's, using rank-based comparison specifically because measured noise on shared runners has a heavy right tail (OS scheduling jitter) that biases mean-based tests. Effect size is estimated via the Hodges-Lehmann median pairwise difference. A shift is flagged only if it is *both* statistically significant *and* larger than $3\times$ the benchmark's measured baseline CV — a fixed percentage threshold was tested first and rejected after Phase 1 measured CVs ranging from 1.38% to 10.54% across benchmarks on identical code. Across the batch, Benjamini-Hochberg FDR correction controls the 5% false-discovery rate across all 78 comparisons rather than per comparison (which alone would produce roughly 4 spurious flags by chance).

The detector was validated before running on real history (`validation/`): same code run twice showed no flag (`-0.21%`, $p=0.520$), a synthetic 8% injected slowdown was correctly flagged (`+6.66%`, $p=3.02\times 10^{-11}$), and a synthetic 1% injected slowdown was correctly *not* flagged despite statistical significance (`+1.08%`, $p=0.0042$) because it sat inside the `4.01%` noise floor.

## Sub-threshold candidate (`8f5d947`) — Resolved via Assembly & Ablation

In addition to the 5 sequential flags above, commit `8f5d947` (*"automata: make behavior more consistent when `WhichCaptures::None` is used"*) showed a smaller slowdown on `find_iter_userid` that stayed below the single-commit pairwise $3\times\text{CV}$ floor (`+2.95%`, $p=3.38\times 10^{-4}$, floor `5.19%` with `ddof=1` or `5.06%` with `ddof=0`), so it was not part of the 5 batch flags. Series-level E-Divisive (`changepoint`) flagged a `+2.53%` structural step at `8f5d947` ($p=0.020$), and historical 30-pair interleaved A/B (`compare-interleaved --pairs 30`) measured `+4.10%` ($\text{CI}_{95}[+3.68\%, +4.51\%]$, $p=1.86\times 10^{-9}$ floor; `+4.31%` wall-clock and `+4.26%` `_rdtsc` hardware cycles on local Intel Alder Lake hardware).

To determine whether `8f5d947` added real runtime work or a binary-layout shift, we inspected the full LTO x86_64 release assembly (`bench.s`, `lto = true`, `codegen-units = 1`), built a same-commit ablation (`8f5d947-ablation`, removing only `self.imp.info.captures_disabled() ||`), and generated a differential flamegraph ([`../assets/flamegraphs/flamegraph_diff_8f5d947.svg`](../assets/flamegraphs/flamegraph_diff_8f5d947.svg)):

- **Instruction count in `bench_find_all`** ([`results/ablation_8f5d947_instructions.json`](results/ablation_8f5d947_instructions.json)): All internal strategy functions (`hybrid::search::find_fwd`, `Core::search_slots`, `ReverseInner`, `ReverseSuffix`, `Memchr3`, `Teddy`) had **+0 instruction change**. In the inlined `FindMatches::count` loop inside `bench_find_all`, instructions rose from **69 static / 60 dynamic instructions per match** (`977feeb`) to **71 static / 62 dynamic instructions per match** (`8f5d947`) — `+2` instructions per match (`cmpb $2, 138(%rcx); je`, `+4,007` dynamic instructions per 2,000-match iteration), plus `+3` stack loads `(%rsp)` per match (`6` → `9`) due to register spills.
- **Same-hash ablation (`8f5d947-ablation vs 8f5d947`, 30 interleaved pairs)**: Removing only `self.imp.info.captures_disabled() ||` reverts the inner loop to **69 static / 60 dynamic instructions per match** (identical to `977feeb`) while keeping `8f5d947`'s doc comments and `rustc` crate `#[doc]` symbol hash fixed. Comparing `8f5d947-ablation` vs `8f5d947` isolated the `captures_disabled()` check at **`+0.08%` wall-clock** ($\text{CI}_{95}[-0.54\%, +0.58\%]$, $p=0.804$, `ok`) and **`+0.06%` `_rdtsc` cycles** ($p=0.839$, `ok`).
- **LTO binary-layout component (`977feeb vs 8f5d947-ablation`, 30 pairs)**: Comparing `977feeb` against `8f5d947-ablation` (**+0 executed instructions**; differs only in `///` doc comments that alter `rustc`'s crate HIR hash and LTO function merge order) shifted `find_iter_userid` by **`+3.27%` wall-clock** ($p=1.92\times 10^{-6}$) and **`+3.28%` `_rdtsc` cycles**. Thus the observed shift on `8f5d947` is dominated by LTO binary layout rather than the `captures_disabled()` branch.

## Calibrated layout floor (post hoc)

Study 3's published metrics above (`1,250` comparisons, `371` flags, `328` false positives = `88.4%` `[84.75%, 91.28%]`, `42` layout artifacts, `1` confirmed, `0` unreviewed) remain unchanged. Post hoc, [`core/layout_floor.py`](../core/layout_floor.py) tests whether calibrating a per-benchmark minimum noise floor from null-control builds cuts cross-build false positives offline using only `data/regex_study3_history.json.gz`.

- **Split & calibration rule**: The `29` null-control commits (`18` Cargo/version/dependency bumps, `7` doc/comment/changelog commits, `4` CI/ignore/test-only commits) are split into two disjoint halves with fixed seed `42` (`14` and `15` commits). On each calibration half, we compute per-benchmark `layout_floor = 3 * SD` (`ddof=1` across signed calibration shifts) and run `compare_distributions(..., min_noise_floor_pct=layout_floor)` + BY-FDR (`alpha=0.05`) strictly on the held-out null commits plus the `21` non-null commits, then swap halves (calibration commits are never evaluated).

The trade-off is lower sensitivity to moderate `+5%` to `+15%` single-build shifts on layout-sensitive benchmarks (`+8%` `validate_adapter_synthetic` drops from `24/25` to `14/25` and `11/25`; held-out `+8%` injection drops from `85.1%` to `47.7%`), and FP/flagged remains high (`88.89%`–`91.67%`) because only one confirmed slowdown exists in the 50 transitions and host-drift commit `30390ec` causes 9–10 of the remaining flags.

## Known limitation of this run

Study 1 ran on a single shared vCPU sandbox with no `cpufreq` governor access and no CPU pinning. Re-measuring the 50-rep baseline on local hardware (Intel Alder Lake, High Priority) reduced `find_iter_userid` CV by 10× (`10.54%` → `1.03%`). Note that in the `20260813T150528_baseline` sandbox run, `is_match_status` was measured before `IS_MATCH_BATCH = 500` batching was added (`mean = 49.76 ns`), whereas Study 1 and Study 2 batched 500× (`9.4–25 µs`):

| Benchmark | Sandbox CV (50 reps, unpinned) | Local Hardware CV (50 reps, High Priority) | Bare-Metal Linux (`isolcpus`) CV |
|---|---|---|---|
| `compile_moderate` | 1.38% | **2.13%** (median 2,032,300 ns) | *not run (Windows host)* |
| `find_iter_userid` | 10.54% | **1.03%** (median 126,900 ns) | *not run (Windows host)* |
| `is_match_status` | 1.89% *(unbatched ~50 ns)* | **3.58%** (median 24,900 ns) | *not run (Windows host)* |
